# SC-FE-01..03 -- decisions made without an explicit governing requirement (PROPOSALS, not product rules)

Batch 02A, Seller Console. Every item below was decided by the implementing session because the governing designs
(ADU-CONSOLE-02 v4.3, ADU-ONB-01 v3.2, ADU-AUTH-02 v3.3, effective 24 November 2026 editions) are silent or only
imply it. None is an approved product, API or security rule. Each is either confirmed by the owning backend work
order or replaced. The fixture contracts live in `apps/console/src/contracts/gap-sc.ts` (provisional, never the API
contract) and are tagged `gap-sc-provisional-1`.

| ID | Proposal | Why it was needed | Confirm or replace in |
|---|---|---|---|
| P-01 | Per-Seller access is one call, `seller.access.get`, returning `capabilities[]`, `destinations[]` (a destination the account may not use is ABSENT; `NO_ENTITLEMENT` is present and disabled) and an optional `restriction`. The Console re-asks it on every navigation inside a Seller. | CONSOLE-02 S19/S22 say hide on missing permission and show disabled on missing entitlement, but name no payload. | SC-BE-02 |
| P-02 | The capability strings the Console acts on in this batch are `readiness.resolve`, `admission.manage`, `notifications.view`. An unknown string is never a grant. | AUTH-02's catalogue is not yet an API. | SC-BE-02 |
| P-03 | Home is one call, `seller.home.get`: `mode` (READINESS_HUB or OPERATING_BRIEF), `role_view`, `areas[]` (state AVAILABLE, DEFERRED or NO_ENTITLEMENT, never a count), `alerts[]` and `obligations[]` as codes. A code this version does not know is shown through an `unknown` sentence with the code, never dropped. | CONSOLE-02 S29-S32 describe the brief but its nonfinancial content is not specified. | SC-BE-03 and owning domains |
| P-04 | A Seller summary carries `publication` (NEVER_PUBLISHED, PUBLISHED, UNPUBLISHED) beside `status` (DRAFT, ACTIVE, SUSPENDED), so "Unpublished" and "Restricted" can be shown. | The brief asks for unpublished and restricted presentations; ONB-01 defines only the lifecycle. | SC-BE-03 |
| P-05 | Admission offers ONE working method, a one-time code sent to the verified phone and sent as a DM from the claimed account to the official Adulis account (ONB-01 S49-S58). Direct platform connection is shown disabled with the reason "needs the platform to approve Adulis first". The fixture operation is `seller.social.start`. | ONB-01 makes Login Kit primary but its activation needs platform approval. | SC-BE-03 |
| P-06 | Fixture durations are demonstration values only: resend after 2 seconds, rate-limit retry after 30 seconds, code validity 5 minutes (the AUTH-02 S16 default). The demonstration codes (success, incorrect, expired, rate-limited) exist only in the fixture module. | OTP expiry, attempt limits and rate-limit values are open decisions and must not be invented. | SC-BE-02 |
| P-07 | At a deadline the Console asks the server (`auth.otp.status`) whether resend is allowed or the code expired; it never enables or disables a control because its own clock reached a number. | "A countdown may display a server deadline; it may not decide anything when it reaches zero." | SC-BE-02 |
| P-08 | Readiness reason codes `COMPANY_DETAILS_INCOMPLETE`, `STORE_PROFILE_INCOMPLETE`, `FULFILMENT_REQUIRED`, `PRODUCT_REQUIRED` are provisional. ONB-01 S39 names only the admission reasons. | The readiness items need reasons to explain themselves. | SC-BE-03 |
| P-09 | A readiness resolving action carries `denied` (NO_PERMISSION hides the control and the row says who can do it; NO_ENTITLEMENT disables with a reason). | ONB-01 S79 shows `resolving_action: {kind}` only. | SC-BE-03 |
| P-10 | The Seller chooser is always shown after sign-in, even for one Seller. | The design does not say whether a single Seller is entered directly. | Founder |
